# 《东方守幻录》测试策略

这份文档给制作人和后续写代码的人看。它只规定「测什么、什么时候测、怎么记缺陷」。不引入新的测试框架，也不改游戏。

设计稿还在未合并的 PR 里。塔防的预期以这些为准，不以 `main` 上那份车道总纲为准（见 `DESIGN_ISSUES.md` 的 DI-16）：

| 材料 | PR | 测试时拿它核对什么 |
| --- | --- | --- |
| 总纲和路线图 | #3 | 已定规则、明确不做的事、仍标「待你补充」的空位 |
| 战斗规则和 `data/balance/combat/` | #4 | 状态机、伤害、手感时长、`feel.json` |
| 关卡编组和 `tools/validate_levels.py` | #5 | MVP 七关的地图、波次、解锁、星级字段 |
| 叙事和中文表 | #2 | 玩家看见的句子、教学 key、已定名的敌人 |
| 美术规格 | #6 | 分辨率、格子像素、特效时长是否照抄战斗稿 |
| 数值分支 `numeric/touhou-td-framework` | 无 PR | 只作对照。和上面冲突时记缺陷到设计，不把它当成已拍板 |

`main` 上现在能玩的只有标题画面，点开始进入 `scenes/battle/battle_lane.tscn`。那是占位，不是塔防。没有找到塔防核心原型的 PR。原型合并之前，下面第 3 节的「无头关卡模拟」和「人工打完七关」都还跑不了，只保留方案和清单。

Godot 版本以仓库根目录 `godot-version.txt` 为准，当前是 4.7.2。

## 1. 四层测试各管什么

一层不管另一层的事。配置表填错了，不要等人工打一局才发现；手感对不对，也不要指望单元测试。

### 1.1 自动化单元测试（Godot）

**负责**

纯规则，不打开完整关卡画面：

- 伤害公式：`max(攻击 − 护甲, 攻击 × 0.2)`（PR #3 `docs/GDD.md`「局内塔防」）。`min_damage` 是否再托底，等 DI-01 澄清后再加断言
- 状态叠加、减速只取最强、冻结时速度为 0（PR #4 `docs/design/combat/core_rules.md`、`damage_and_status.md`）
- 波次状态机的转移：布阵、出怪、胜利、失败、最后一波不弹三选一。转移条件以澄清后的 DI-03、DI-05 为准；澄清前只测「代码和它自己声明的那张状态表一致」，并在测试名里写上依据的文件
- 存档能记下「每一波开始时的局内状态」，否则做不到从当前波重来（PR #3 `docs/ROADMAP.md` 第 1 节）
- 关卡 JSON 被程序读入后，槽位、路径、可放置角色和文件一致。PR #5 已有 `tests/unit/test_level_data.gd` 的方向，合并那条 PR 后再在塔防代码上补断言

**不负责**

画面闪不闪、好不好玩、某关会不会太难。那些归 1.4 和 `LEVEL_SIM.md`。

**用什么跑**

仓库已经在用 GUT：`addons/gut/`、`.gutconfig.json`、`ci/run_tests.sh` 里的 `godot --headless -s addons/gut/gut_cmdln.gd`。建议继续用 GUT。战斗策划在 PR #4 `docs/design/combat/README.md` 9.4 也建议伤害和波次写成纯函数，用 GUT 测。

gdUnit4 也能做 Godot 单元测试，但这个仓库没有它。不要为了这份 QA 文档再加一套框架。引入 gdUnit4 必须另开 PR，并写一篇 ADR，说明为什么 GUT 不够。

不要手改 `addons/gut/`。

**什么时候跑**

- 每次开发 PR：本机 `./ci/run_tests.sh`，CI 的 `test` 作业也会跑
- 只改中文文案、且没有改 key 的 PR：仍跑一遍，确认导入不报错。不必为标点新增用例
- `main` 上现有的 `tests/unit/test_scenes.gd` 等锁的是车道占位。塔防原型换掉场景时，要同时改这些用例，否则 CI 会保护已经作废的画面（DI-16）

### 1.2 配置表校验

**负责**

文件自己是否自洽，不模拟战斗：

- JSON 能解析，关卡符合 `data/levels/level.schema.json`
- 地图 7×12，路径上下左右相连，`.` 和 `slots` 一一对应且贴着路线
- 波次威胁合计等于难度表预算。公式在 PR #5 `docs/design/level/data_format.md`：`round((10 + 4 × 波次) × threat_budget_coef)`
- 可放置名单跟着 `unlock_character_ids` 走
- 刷怪窗口、布阵秒数、波间秒数这些字段填在允许范围内（见 `tools/validate_levels.py` 的 `timing_problems`）
- 文本 key 在 CSV 里存在，教学 key 形如 `tut.<关卡id>.NNN`（PR #2）

**现成工具**

PR #5 的 `tools/validate_levels.py` 已经覆盖地图、威胁、解锁链、星级字段和七关的计时字段。合并后应在 CI 的 lint 里调用（那条 PR 的工作流已有这个方向）。

**建议以后扩展，本 PR 不实现**

另开小 PR，不要和玩法改动混在一起：

1. 关卡里的 `enemy_id` 必须在战斗表里有定义。
2. `enemy_catalog.json` 的 `threat_points` 和 `stats.json` 的 `threat_points` 不一致时直接失败（现在就是 DI-01，校验应报出来，而不是静默选一边）。
3. `ch1_04` 的 `lives_source` 必须真能从 `stats.json` 取到值（现在取不到，见 DI-07）。
4. `characters.json` 的 `unlock` 和 `character_roster.json` 的 `unlocked_by_clearing` 不一致时失败。
5. `feel.json` 里用作秒数的字段必须是非负数字。这一项只查类型，不判断好不好看。
6. 标成 `pending_numbers` 或 `placeholder` 的字段，校验打印「待定」，不要把占位当成错误，也不要在校验脚本里填一个「合理的」数字。

**什么时候跑**

- 改了 `data/levels/`、`data/balance/`、`data/text/` 的 PR：合并前必须过校验
- 只改战斗公式代码、没改表：不用为了改表去跑，但 CI 全量跑到它也无妨
- 在 PR #5 合并前，七关校验只在那条分支上存在。审查别的 PR 时不要假设 `main` 已经有 `tools/validate_levels.py`

### 1.3 无头关卡模拟

**负责**

用固定策略把 MVP 七关自动打完，看剩余生命、灵力曲线、通关率，用来发现相邻关卡难度突然跳变。方案在 `LEVEL_SIM.md`。这里不实现。

**不负责**

代替人工判断「爽不爽」。模拟输出是数字；好不好玩仍要人看 `feel.json` 里的反馈有没有出现。

**什么时候跑**

塔防核心原型（格子、沿路线移动、在 `.` 上放置、自动攻击、灵力、生命、波次、胜负）合并之后再做。在 DI-01、DI-03、DI-06 澄清前，模拟可以跑，但结果只能标「受阻」，不能当成关卡通过或失败。阈值没定之前，不要让 CI 因为「剩命差了几条」变红。

### 1.4 人工体验测试

**负责**

人眼和手指才能判断的事，清单在 `MVP_ACCEPTANCE.md`：

- 每一关是不是只多教一件新东西，新手会不会在提示出现前卡住
- 节奏（在 DI-03、DI-04 澄清之后才能判过）
- 命中闪白、伤害数字、击倒光点、符卡立绘、冰碎，是否按 `feel.json` 和 `rules.json` 里的时长出现
- 教学句子和实际手势是否一致（现在不一致，见 DI-12，澄清前这条预期就是「已知设计问题」）

**什么时候跑**

- 第一次做出可玩的七关时，按清单从头打到 `ch1_04`
- 以后改了某一关的地图、波次、教学句或 `feel.json`，重打这一关和它的前一关（看难度有没有突然变）
- 改了胜利、失败、存档、三选一，把序章第 3 关（第一次三选一）和 `ch1_04`（首领）再打一遍
- 纯重构、测试证明行为不变：可以不重打，PR 里写明依据

人工测试不编「必须几个人」。设计文档没有这个人数。记录实际试玩的人数即可。方法写在验收清单的学习曲线一节。

## 2. 每个开发 PR 的审查清单

审查人按顺序看。做不到的那一条要在 PR 里写原因，不能留空。

- [ ] 这个 PR 只做一件事，标题是英文 Conventional Commits，正文是简体中文，写了改了什么、为什么、怎么验证
- [ ] 没有直接改 `main`。分支名是 `feature/`、`fix/`、`chore/`、`docs/` 之一（云端代理若必须用 `cursor/` 前缀，在正文里说明）
- [ ] 玩法有变时，同一 PR 更新了受影响的文档。总纲里标「待你补充」的句子没有被改成定案
- [ ] 新的平衡数字在 `data/balance/`，不在场景脚本里写死
- [ ] 没有把 DI-01 到 DI-17 里仍冲突的数字选一个写进代码并当成最终规则。若原型必须临时用一个数才能跑，PR 正文写「临时，依据某文件某字段」，并链到对应的 DI
- [ ] 行为变化有测试，或说明为什么现有 GUT 已经覆盖
- [ ] 改了界面就有截图。竖屏可以只截 1080×1920 这一档，除非这次改的是刘海或长屏底栏（PR #6）
- [ ] 没有密钥、keystore、密码、`.env`
- [ ] 没有手改 `addons/gut/`
- [ ] 没有多人、服务器、账号、抽卡、体力、付费、内购、广告、弹幕射击（PR #3「明确不做」）
- [ ] 没改 Godot 版本；若改了，文档、CI 和一篇 ADR 同时在
- [ ] 关卡或战斗表有改时，配置校验的结果贴在 PR 里
- [ ] 玩家能看见的中文用了术语表里的词：角色不叫「塔」，守护点不叫「基地」，敌人叫「残影」（PR #2 `docs/design/narrative/glossary.md`）

## 3. 缺陷严重程度

等级看玩家能不能继续玩、和已经定下来的规则差多远。例子都用《东方守幻录》里的事。设计稿自己还矛盾的项，先记在 `DESIGN_ISSUES.md`，不要报成程序 S0。

### S0 阻断

游戏或进度坏了，或者违反已经写死的「明确不做」。

例子：

- 标题画面无法进入任何关卡，或一进关卡就崩溃
- 存档写坏，已通关的关卡和局外等级消失
- 守护点生命已经到 0 仍显示胜利，或生命还有剩余却无法结算
- 出现付费、内购、广告、抽卡或联网登录

### S1 严重

MVP 的一条主路径走不通，或和已定规则相反，但游戏还能打开。

例子：

- 按关卡 JSON，角色可以放在 `P` 路线上，或 `.` 槽位点了没反应，导致这一关无法布阵
- 最后一波打完后仍然弹出三选一，挡住结算（PR #3、PR #4 已定：最后一波后直接结算）
- 序章第 1 关首通就能放魔理沙或琪露诺（加入时机已定：魔理沙要通关 `prologue_01`，琪露诺要通关 `ch1_01`）
- 从当前波重来后，规则要求恢复的那些字段丢了（字段清单等 DI-05 定稿后再用定稿判断）
- 七关里某一关的教学提示把玩家带进死路，不看外部说明就无法过关。`ch1_04` 在 DI-06 拍板前打不过，先记设计问题，不记 S1

### S2 一般

能通关，但和已定的反馈、星级或文案不一致，需要再打一局才能确认。

例子：

- 命中闪白明显不是 `feel.json` 里 `hit_flash.duration_sec` 的 0.08 秒（长到能数出来，或短到看不见）
- 击倒光点没有飞向灵力栏，或飞行时间和 `kill_burst.fly_duration_sec`（0.5 秒）差一截
- 星星显示和剩余生命对不上：满命 20/20 没有 3 星，或没通关却给了星
- 波次横幅不出现，但下一波仍正常开始
- 教学句和手势不一致。在 DI-12 改文案之前，这是已知设计差，修文案的 PR 才按 S2 回归

### S3 轻微

不影响操作和胜负。

例子：

- 某个失物簿句子有错字
- 伤害数字颜色和 `feel.json` 的 `damage_numbers.normal_color` 略有偏差，但仍是浅色、能读
- 敌人图鉴用了「普通残影」，术语表已定名「小残影」（玩家仍知道在说路上的杂兵）
- 音效少一下，画面反馈还在

## 4. 缺陷报告模板

复制下面这一段，填到 GitHub issue。仓库已有 `.github/ISSUE_TEMPLATE/bug_report.yml`（发生了什么、期望、步骤、截图、版本），提交时加上这里的严重程度、关卡 id 和设计出处。不要只写「手感不对」。

```markdown
## 标题
fix: <一句话，玩家看见的现象>

## 严重程度
S0 / S1 / S2 / S3

## 关卡
prologue_01 / … / ch1_04 / 标题画面 / 无关卡

## 发生了什么

## 期望发生什么
写出依据：PR 编号、文件路径、小节或 JSON 字段。
若依据落在 DESIGN_ISSUES.md，写 DI 编号，并说明这是程序做反了，还是设计仍待定。

## 怎么重现
1.
2.
3.

## 实际数字（能量到的才填）
- 剩余生命：
- 灵力：
- 波次：
- 倍速：1× 或 2×
- 随机种子（无头模拟才有）：

## 版本
- 分支和提交：
- Godot：4.7.2 或实际使用的版本
- 手机型号 / 编辑器 / 无头：

## 截图或录屏

## 会不会挡 MVP
是 / 否。否的话写下一关还能不能进。
```

已知的设计矛盾不要用这份模板重复开一堆 S1。先看 `DESIGN_ISSUES.md`。只有实现和「已经对齐的那一句」相反时，才开缺陷。
